# Контекст Android-приложения TrainingApp

> **Важно:** Замечания, даваемые пользователем в процессе разработки, имеют высший приоритет. Этот файл хранит накопленный контекст; при конфликте с ним — уточнять у пользователя как поступить.

## О проекте
Android-приложение для занятий силовыми видами спорта.

## Структура проекта
Полное и актуальное описание структуры проекта (модули, папки, назначение) находится в файле **[`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md)**.

- **[`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md) нужно обновлять после любых изменений в структуре проекта** — добавление/удаление модулей, папок, ключевых файлов.
- При добавлении нового Gradle-модуля: обновить и [`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md), и [`settings.gradle.kts`](settings.gradle.kts).
- **В каждом новом модуле нужно создавать свои файлы `AGENTS.md` и `MODULE_STRUCTURE.md`**. В `AGENTS.md` добавлять ссылку на `MODULE_STRUCTURE.md` — файл со структурой этого модуля, описывающий внутреннюю структуру и назначение элементов модуля. Этот файл также нужно поддерживать в актуальном состоянии. На уровне `Android/` используется `PROJECT_STRUCTURE.md` (структура всего проекта), в модулях — `MODULE_STRUCTURE.md` (структура конкретного модуля).

## Архитектурные и стилистические замечания

### Язык и общение
- Общаться на русском языке (включая субагентов).
- Комментарии в коде дублировать на двух языках: сначала на английском, затем на русском (в той же строке или в соседних строках).
- Описывать подробно все действия, будто собеседник не разбирается в теме.

### Архитектура
- **Многомодульный проект**: каждая фича лежит в отдельном модуле в папке `features/`. Модуль `app` — точка сборки, не содержит бизнес-логики.
- **Отделение бизнес-логики от UI**: UI-слой (Composable/View) не содержит бизнес-логики. Бизнес-логика — в отдельных классах (UseCase/Interactor/Repository), доступных через DI. UI только отображает состояние и отправляет намерения.
- **Стек**: Kotlin + Jetpack (AndroidX, Coroutines, Flow). DI — Hilt. БД — Room (предполагается). Сеть — Retrofit (предполагается). Точные версии — в `Android/gradle/libs.versions.toml`.
- **DI (Hilt)**: при написании кода с Hilt-аннотациями (`@HiltAndroidApp`, `@AndroidEntryPoint`, `@HiltViewModel`, `@Inject`, `@Module`, `@Provides`, `@Binds`, `@InstallIn`, `@Singleton` и др.) обязательно объяснять в комментарии рядом, что означает каждая аннотация — разработчик не знаком с Hilt и учится по ходу.
- **UI-фреймворк**: XML Views + ViewBinding (без DataBinding). Архитектура UI-агностична — бизнес-логика не зависит от способа отрисовки. В будущем можно начать писать новые экраны на Jetpack Compose и постепенно мигрировать старые без переписывания бизнес-логики.
- **Паттерн**: MVVM + Clean Architecture (ViewModel + UseCase + Repository). Единый `UiState` (data class) на экран — весь стейт экрана в одной переменной, эмитится через `StateFlow`. UI отправляет намерения (events) в ViewModel, ViewModel обновляет state. Бизнес-логика — в UseCase/Repository, ViewModel не содержит бизнес-правил. UseCase можно опускать для тривиальных операций (ViewModel → Repository напрямую).
- **Асинхронность/Реактивность**: Kotlin Coroutines + Flow. Упор на реактивность — данные текут через `Flow`/`StateFlow`/`SharedFlow`. `suspend`-функции для разовых операций (БД, сеть). `viewModelScope` для запуска корутин в ViewModel. `StateFlow` используется для единого `UiState`. LiveData не используется.
- **Локальная БД**: Room. Описание таблиц через `@Entity`, запросы через `@Dao` с `suspend`-функциями и `Flow` для реактивных запросов. Миграции встроены. Интеграция с Hilt через `@Provides` для `RoomDatabase`.
- **Сеть**: Retrofit + OkHttp. Описание API через интерфейсы с аннотациями (`@GET`, `@POST` и т.д.), `suspend`-функции для Coroutines. OkHttp interceptors для логирования/авторизации. Интеграция с Hilt через `@Provides`.
- **Навигация**: Jetpack Navigation (Navigation Component) с Safe Args. Навигация вынесена в отдельный модуль `core/navigation` — содержит интерфейсы `Screen` (sealed class с маршрутами) и `Navigator` (интерфейс с методами `navigate(screen)`/`back()`). Feature-модули зависят только от `core/navigation` и не знают друг о друге. Реализация `Navigator` и граф навигации (XML/DSL) — в модуле `app`, где есть доступ к `NavController`. `Navigator` инжектируется через Hilt, доступен из ViewModel (бизнес-логика может инициировать переходы, UI-слой не решает "куда перейти").
- **Десериализация JSON**: kotlinx.serialization. Аннотация `@Serializable` на data classes, `@SerialName` для маппинга полей. Интеграция с Retrofit через `retrofit2-kotlinx-serialization-converter`. Плагин компилятора `kotlin("plugin.serialization")`.
- **Интерфейсы для реализаций**: любые реализации (Repository, DataSource, Navigator и т.д.) должны быть закрыты интерфейсами. Классы-реализации инжектируются через Hilt по интерфейсу. Это позволяет легко заменять реализации (например, мок для тестов) и сохраняет слабую связность.
- **Структура feature-модуля**: каждый feature-модуль называется с префиксом `feature-` (например, `feature-auth`, `feature-programs`). Может содержать подмодули: `contract` (контракты/интерфейсы фичи, доступные другим модулям), `domain` (бизнес-логика: UseCase, Repository, модели), `ui` (Fragment/View/ViewModel), `common` (вспомогательный код фичи). Могут быть не все подмодули, но других быть не должно. `domain`-модуль одной фичи не должен зависеть от `domain`-модуля другой фичи.
- **Логирование**: Timber. Инициализация в `Application.onCreate()` через `Timber.plant(DebugTree())` (только в debug-сборке). Автоматический тег по имени класса. Можно расширить своим деревом для production-логирования (файл/краш-репорт).
- **Обработка ошибок/ресурсов**: `Resource<T>` wrapper (sealed class: `Loading` / `Success(data)` / `Error(message, cause)`). Repository возвращает `Flow<Resource<T>>`, ViewModel мапит в `UiState` (поля loading/error/data). Явное моделирование состояния для UI. Внутри Repository можно использовать корутинный try/catch, наружу отдавать `Resource` для предсказуемости.
- **Тестирование**: JUnit4 + Mockito-Kotlin + Turbine + Robolectric. Mockito-Kotlin для моков (`org.mockito.kotlin.verify`), Turbine для тестирования `Flow`/`StateFlow`, Robolectric для тестов с Android-зависимостями (Context, Room) без эмулятора. Hamcrest для ассертов (`org.hamcrest.MatcherAssert.assertThat`).
- **Форматирование дат/времени**: java.time (`LocalDate`, `Instant`, `Duration`, `ZonedDateTime`) + core library desugaring (`coreLibraryDesugaringEnabled = true` в `build.gradle.kts`, зависимость `desugar_jdk_libs`). Позволяет использовать современный Java 8 time API на всех версиях Android (включая minSdk < 26). Интеграция с Room через TypeConverters, с kotlinx.serialization через кастомные сериализаторы.
- **SDK**: minSdk 24 (Android 7.0, охват ~98%), targetSdk 34 (Android 14, актуальная для Google Play), compileSdk 34. Широкий охват устройств + актуальный API.
- **CI/CD**: отложено. В будущем планируется бэкенд на Yandex Cloud — CI/CD настроим вместе с бэкендом (возможно self-hosted runner на ВМ в Yandex Cloud или GitHub Actions). Пока фокус на разработке.
- **Дизайн-система**: Material Design 2 (Material Components for Android). Готовые компоненты (`MaterialButton`, `MaterialCardView`, `TextInputLayout`, `BottomNavigationView`, `Slider`). Поддержка тёмной темы. Без динамических цветов (Material You не используется). При необходимости — кастомные компоненты поверх Material 2.

### Конвенции кода
- Переменные и параметры конструктора располагать в алфавитном порядке.
- Использовать trailing comma (завершающую запятую) в перечислениях значений (enum entries, коллекции, параметры функций/конструкторов).
- Помечать `internal` сущности, которые не предназначены для использования вне своего модуля (например, Room TypeConverters, внутренние реализации). Public оставлять только тому, что используется другими модулями.
- Если класс/интерфейс берётся из артефакта — не декомпилировать, а просить показать сигнатуру.
- Уверенность в ответе оценивать от 1 до 10. Если < 8 — искать ответ в коде/через mcp. Если < 8 и ответ не найден — задавать вопрос. Действовать только при уверенности > 8.
- Сначала отвечать на вопрос, потом писать код.

### Структура замечаний
- Не использовать секцию "История замечаний". Новые замечания добавлять сразу в подходящий подпункт (например, в "Конвенции кода" или "Архитектура"). Если подходящего подпункта нет — создавать новый.

### Сборка
- Для сборки использовать `./gradlew` из папки `Android/`.

### Тесты
- Для проверок в unit-тестах использовать `org.mockito.kotlin.verify` или `org.hamcrest.MatcherAssert.assertThat`.
- Приватные функции располагать внизу класса с тестами.
- Структура теста: переменные → whenever → вызов методов → проверка результатов.
- Предполагать, что тесты написаны с ошибками; запускать с грепом по ключевым словам ошибок.
- `--tests` не поддерживается с `-p`.
