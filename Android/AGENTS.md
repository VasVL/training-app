# Контекст Android-приложения TrainingApp

> **Важно:** Замечания, даваемые пользователем в процессе разработки, имеют высший приоритет. Этот файл хранит накопленный контекст; при конфликте с ним — уточнять у пользователя как поступить.

## О проекте
Android-приложение для занятий силовыми видами спорта.

## Визуальная документация
- Общие визуальные правила находятся в [`VISUAL_STYLE.md`](VISUAL_STYLE.md).
- Утверждённые решения конкретных экранов и их макеты хранятся внутри соответствующей фичи: например, [`feature-auth/UI_DESIGN.md`](features/feature-auth/UI_DESIGN.md) и [`feature-auth/UI_MOCKUPS.html`](features/feature-auth/UI_MOCKUPS.html).

## Структура проекта
Полное и актуальное описание структуры проекта (модули, папки, назначение) находится в файле **[`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md)**.

- **[`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md) нужно обновлять после любых изменений в структуре проекта** — добавление/удаление модулей, папок, ключевых файлов.
- При добавлении нового Gradle-модуля: обновить и [`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md), и [`settings.gradle.kts`](settings.gradle.kts).
- **В каждом новом модуле нужно создавать свои файлы `AGENTS.md` и `MODULE_STRUCTURE.md`**. В `AGENTS.md` добавлять ссылку на `MODULE_STRUCTURE.md` — файл со структурой этого модуля, описывающий внутреннюю структуру и назначение элементов модуля. Этот файл также нужно поддерживать в актуальном состоянии. На уровне `Android/` используется `PROJECT_STRUCTURE.md` (структура всего проекта), в модулях — `MODULE_STRUCTURE.md` (структура конкретного модуля).

## Архитектурные и стилистические замечания

### Язык и общение
- Общаться на русском языке (включая субагентов).
- Комментарии в коде дублировать на двух языках: сначала на английском, затем на русском (в той же строке или в соседних строках).
- Описывать подробно все действия, будто собеседник не разбирается в теме.

### Согласование изменений
- После каждого изменения файла приложения, кроме технических HTML-макетов с уже утверждённым дизайном, предоставлять пользователю ссылку на изменённый файл и ждать одобрения перед следующим изменением.
- После согласования единого механического изменения можно без дополнительных подтверждений применить его во всех затронутых файлах: например, переименовать идентификатор и обновить его использования либо заменить повторяющееся значение общим ресурсом. Исключение действует только пока изменения не вносят нового смысла, поведения или самостоятельного дизайнерского решения.
- Реализовывать фичи небольшими завершёнными итерациями, каждая из которых пригодна для отдельного коммита. Перед созданием коммита обязательно получать разрешение пользователя. Это позволяет проверять изменения небольшими и понятными diff-группами.

### Архитектура
- **Многомодульный проект**: каждая фича лежит в отдельном модуле в папке `features/`. Модуль `app` — точка сборки, не содержит бизнес-логики.
- **Общий код**: `core/common` — только контейнер узких общих модулей. Не размещать код или ресурсы прямо в нём: выбирать модуль по назначению (`common:domain` для чистых Kotlin-типов, `common:logging` для логирования, `common:ui` для общих UI-ресурсов) либо создавать новый при появлении самостоятельного назначения. Чистые `domain`, `contract` и `core:navigation` — Kotlin/JVM-модули; Android-плагин применять только модулям, которым нужен Android API, ресурсы или Android-инфраструктура.
- **Отделение бизнес-логики от UI**: UI-слой (Composable/View) не содержит бизнес-логики. Бизнес-логика — в отдельных классах (UseCase/Interactor/Repository), доступных через DI. UI только отображает состояние и отправляет намерения.
- **Данные для сценария**: метод репозитория и запрос DAO должны возвращать только поля, нужные конкретному сценарию. Для списка создавать отдельную проекцию, а не загружать полную сущность; маппинг выполняется последовательно между database, domain и UI-слоями.
- **UI-сущности**: `UiState` и связанные с ним UI-сущности не используют domain-модели или domain-enum'ы. Для отображаемых данных создавать отдельные UI-сущности и enum'ы, преобразуя их в маппере UI-слоя. Каждый экран всегда обрабатывает взаимоисключающие `Loading`, `Error` и `Ready` состояния. `Error` передаёт причину как UI-enum, а Fragment выбирает локализованный текст из ресурсов; исключение и технические детали остаются только в логах. Причина должна быть конкретной для пользователя, а не общим названием операции: например, отдельно «профиль не найден» и «не удалось записать данные в базу».
- **Одноразовые UI-события**: действия, которые нужно обработать ровно один раз и не восстанавливать после пересоздания UI (показ Snackbar/диалога, открытие системного пикера, кратковременная ошибка сохранения), объявлять как `UiAction` и передавать через `SharedFlow`. Долговременные отображаемые данные и блокирующие ошибки загрузки остаются в `UiState`/`StateFlow`.
- **Формат логов**: лог вызова функции начинать с её имени и перечислять параметры в формате `functionName: parameter1=$parameter1, parameter2=$parameter2`; остальные логи строить в той же структуре с явным действием и результатом. Чувствительные персональные данные, токены и пароли в логи не записывать.
- **Пакеты UI по экранам**: когда UI-модуль содержит два и более экрана, группировать код по экранным пакетам. Fragment остаётся в корне своего экранного пакета, а `adapter`, `entity`, `mapper` и `viewmodel` располагаются в его подпапках.
- **Стек**: Kotlin + Jetpack (AndroidX, Coroutines, Flow). DI — Hilt. БД — Room (предполагается). Сеть — Retrofit (предполагается). Точные версии — в `Android/gradle/libs.versions.toml`.
- **DI (Hilt)**: при написании кода с Hilt-аннотациями (`@HiltAndroidApp`, `@AndroidEntryPoint`, `@HiltViewModel`, `@Inject`, `@Module`, `@Provides`, `@Binds`, `@InstallIn`, `@Singleton` и др.) обязательно объяснять в комментарии рядом, что означает каждая аннотация — разработчик не знаком с Hilt и учится по ходу.
- **UI-фреймворк**: XML Views + ViewBinding (без DataBinding). Для адаптивной компоновки XML-разметок преимущественно использовать `ConstraintLayout`. Если для секции достаточно одного простого вертикального или горизонтального уровня, использовать более лёгкий `LinearLayout`; для единственного содержимого или наложения элементов — `FrameLayout`. Архитектура UI-агностична — бизнес-логика не зависит от способа отрисовки. В будущем можно начать писать новые экраны на Jetpack Compose и постепенно мигрировать старые без переписывания бизнес-логики.
- **Производительность XML-разметок**: минимизировать число уровней вложенности и не добавлять `ViewGroup` без необходимости. Не использовать Material-обёртки (`MaterialCardView` и подобные) только ради фона, скругления, обводки или ripple: если требуемое поведение можно получить у стандартного `View` через drawable, использовать этот вариант. Material-компонент оставлять, когда нужны его специфические возможности.
- **Паттерн**: MVVM + Clean Architecture (ViewModel + UseCase + Repository). Единый `UiState` на экран эмитится через `StateFlow`. `UiState` объявлять как `sealed interface` со взаимоисключающими состояниями `Loading`, `Ready` и `Error`; данные, нужные для отображения, хранятся в соответствующем состоянии. UI отправляет намерения (events) в ViewModel, ViewModel обновляет state. Бизнес-логика — в UseCase/Repository, ViewModel не содержит бизнес-правил. UseCase можно опускать для тривиальных операций (ViewModel → Repository напрямую).
- **Асинхронность/Реактивность**: Kotlin Coroutines + Flow. Упор на реактивность — данные текут через `Flow`/`StateFlow`/`SharedFlow`. `suspend`-функции для разовых операций (БД, сеть). `viewModelScope` для запуска корутин в ViewModel. `StateFlow` используется для единого `UiState`. LiveData не используется.
- **Обновление StateFlow**: если новое значение зависит от текущего, изменять `MutableStateFlow` через атомарный `update { state -> … }`, а не отдельно читать и записывать `.value`.
- **Локальная БД**: Room. Описание таблиц через `@Entity`, запросы через `@Dao` с `suspend`-функциями и `Flow` для реактивных запросов. Миграции встроены. Интеграция с Hilt через `@Provides` для `RoomDatabase`.
- **Сеть**: Retrofit + OkHttp. Описание API через интерфейсы с аннотациями (`@GET`, `@POST` и т.д.), `suspend`-функции для Coroutines. OkHttp interceptors для логирования/авторизации. Интеграция с Hilt через `@Provides`.
- **Навигация** (распределённый подход): Jetpack Navigation (Navigation Component) с Safe Args.
  - `core/navigation` содержит базовый маркерный интерфейс `Screen` (без тел, просто маркер) и интерфейс `Navigator` с методами `navigate(screen)`/`back()`/`popUpTo(screen, inclusive)`.
  - Каждая фича объявляет свои экраны в своём **contract-модуле** как `sealed interface XxxScreen : Screen` с объектами/data class для конкретных маршрутов (например, `ProgramScreen.List`, `ProgramScreen.Detail(programId)`). Contract-модуль зависит от `core/navigation`.
  - Модуль `app` зависит от всех contract-модулей и реализует `Navigator` — маппинг каждого `Screen` в конкретное действие навигации (`NavDirections`). Граф навигации (XML/DSL) — в `app`, где есть доступ к `NavController`.
  - `Navigator` инжектируется через Hilt, доступен из ViewModel (бизнес-логика может инициировать переходы, UI-слой не решает "куда перейти").
  - Feature-модули зависят только от `core/navigation` и своего contract-модуля, не зная друг о друге.
  - Диплинки отложены (MVP без них).
- **Десериализация JSON**: kotlinx.serialization. Аннотация `@Serializable` на data classes, `@SerialName` для маппинга полей. Интеграция с Retrofit через `retrofit2-kotlinx-serialization-converter`. Плагин компилятора `kotlin("plugin.serialization")`.
- **Интерфейсы для реализаций**: любые реализации (Repository, DataSource, Navigator и т.д.) должны быть закрыты интерфейсами. Классы-реализации инжектируются через Hilt по интерфейсу. Это позволяет легко заменять реализации (например, мок для тестов) и сохраняет слабую связность.
- **Структура feature-модуля**: каждый feature-модуль называется с префиксом `feature-` (например, `feature-auth`, `feature-programs`). Может содержать подмодули: `contract` (контракты/интерфейсы фичи, доступные другим модулям), `domain` (бизнес-логика: domain-модели, enum-ы, интерфейсы репозиториев, use-case), `data` (реализации репозиториев + мапперы Room Entity ↔ domain-модель + Hilt-биндинги; зависит от `domain` фичи и `core/database`), `ui` (Fragment/View/ViewModel), `common` (вспомогательный код фичи). Могут быть не все подмодули, но других быть не должно. `domain`-модуль одной фичи НЕ зависит от `domain`-модуля другой фичи. Зависимости между фичами — только через `contract`-модули. Persistence изолирована за портами (Ports & Adapters / Clean Architecture): `domain` объявляет интерфейсы репозиториев, `data` реализует их через DAO из `core/database`.
- **Структура `domain`-подмодуля фичи** (минимальный набор папок):
  - `entity/` — data class-ы (domain-модели, без Room-аннотаций).
  - `entity/type/` — enum-ы для domain-моделей.
  - `repository/` — интерфейсы репозиториев (контракты для `ui` и `data`).
  - `usecase/` — use-cases (interactors); папка создаётся только когда появляется первый use-case, заранее не создавать.
  - `service/`, `policy/`, `event/`, `exception/` — не создавать заранее; добавлять по мере необходимости.
  - **Ничего не класть в корень `domain`-пакета**: каждый файл должен лежать в подходящей подпапке. Если ни одна существующая папка не подходит — советоваться с пользователем (создавать новую или положить в существующую).
- **Структура `data`-подмодуля фичи** (минимальный набор папок):
  - `mapper/` — классы-мапперы (Room Entity ↔ domain-модель), классы с методами `map`, помеченные `@Singleton @Inject`.
  - `repository/` — реализации репозиториев (имплементируют интерфейсы из `domain/repository`).
  - `di/` — Hilt-модули (`@Module @InstallIn(SingletonComponent)`, `@Binds` интерфейс→реализация).
  - **Ничего не класть в корень `data`-пакета**: каждый файл в подходящей подпапке; если не подходит — советоваться с пользователем.
- **Логирование**: Timber. Инициализация в `Application.onCreate()` через `Timber.plant(DebugTree())` (только в debug-сборке). Автоматический тег по имени класса. Можно расширить своим деревом для production-логирования (файл/краш-репорт).
- **Диагностическое логирование**: добавлять Timber-логи на входе ключевых пользовательских действий, при смене `UiState`, успешных операциях и обработке ошибок, чтобы поведение можно было восстановить по журналу. Не логировать секреты и чувствительные персональные данные: пароли, токены, ключи, платёжные реквизиты, номера документов и аналогичные значения.
- **Обработка ошибок/ресурсов**: `Resource<T>` wrapper (sealed class: `Loading` / `Success(data)` / `Error(message, cause)`). Repository возвращает `Flow<Resource<T>>`, ViewModel мапит в `UiState` (поля loading/error/data). Явное моделирование состояния для UI. Внутри Repository можно использовать корутинный try/catch, наружу отдавать `Resource` для предсказуемости.
- **Тестирование**: JUnit4 + Mockito-Kotlin + Turbine + Robolectric. Mockito-Kotlin для моков (`org.mockito.kotlin.verify`), Turbine для тестирования `Flow`/`StateFlow`, Robolectric для тестов с Android-зависимостями (Context, Room) без эмулятора. Hamcrest для ассертов (`org.hamcrest.MatcherAssert.assertThat`).
- **Форматирование дат/времени**: java.time (`LocalDate`, `Instant`, `Duration`, `ZonedDateTime`) + core library desugaring (`coreLibraryDesugaringEnabled = true` в `build.gradle.kts`, зависимость `desugar_jdk_libs`). Позволяет использовать современный Java 8 time API на всех версиях Android (включая minSdk < 26). Интеграция с Room через TypeConverters, с kotlinx.serialization через кастомные сериализаторы.
- **SDK**: minSdk 24 (Android 7.0, охват ~98%), targetSdk 34 (Android 14, актуальная для Google Play), compileSdk 34. Широкий охват устройств + актуальный API.
- **CI/CD**: отложено. В будущем планируется бэкенд на Yandex Cloud — CI/CD настроим вместе с бэкендом (возможно self-hosted runner на ВМ в Yandex Cloud или GitHub Actions). Пока фокус на разработке.
- **Дизайн-система**: Material Design 2 (Material Components for Android). Готовые компоненты (`MaterialButton`, `MaterialCardView`, `TextInputLayout`, `BottomNavigationView`, `Slider`). Поддержка тёмной темы. Без динамических цветов (Material You не используется). При необходимости — кастомные компоненты поверх Material 2.

### Процесс проектирования UI
- Перед созданием нового экрана или заметным изменением существующего UI сначала показывать пользователю макет и получать его согласование.
- После согласования дизайна сохранять только утверждённые макеты и описания в папке соответствующей фичи.
- После согласования дизайна можно создавать или обновлять технический HTML-макет без отдельного согласования его полного содержимого.

### Конвенции кода
- Переменные и параметры конструктора располагать в алфавитном порядке.
- Использовать trailing comma (завершающую запятую) в перечислениях значений (enum entries, коллекции, параметры функций/конструкторов).
- Помечать `internal` сущности, которые не предназначены для использования вне своего модуля (например, Room TypeConverters, внутренние реализации). Public оставлять только тому, что используется другими модулями.
- `companion object` располагать внизу класса.
- Не использовать в коде полные имена классов и функций; вместо них добавлять необходимые `import`.
- Для Kotlin-вызова с одним аргументом, если смысл понятен из имени метода и аргумента (например, `render(uiState)`), именованный аргумент не нужен. При двух и более аргументах использовать именованные аргументы, кроме стандартных и очевидных вызовов API. Именованные аргументы обязательны для неочевидных значений, особенно `Boolean`, чисел, `null` и нескольких аргументов одного типа. Если в вызове использован хотя бы один именованный аргумент, именованными должны быть все аргументы этого вызова.
- При вызове Java-метода, если назначение аргумента не очевидно, добавлять перед ним комментарий формата `/* parameterName = */`. Не добавлять такие комментарии механически к каждому Java-вызову. Если такой комментарий добавлен хотя бы к одному аргументу вызова, добавлять его ко всем аргументам этого вызова.
- В `when`, если для одного варианта состояния используется проверка типа `is`, использовать `is` для всех вариантов, включая `object`/`data object`.
- Для каждого `RecyclerView` в XML-разметке указывать preview-элемент через `tools:listitem`; при необходимости дополнительно задавать `tools:itemCount` и `tools:visibility`, чтобы список отображался в редакторе.
- Если класс/интерфейс берётся из артефакта — не декомпилировать, а просить показать сигнатуру.
- Уверенность в ответе оценивать от 1 до 10. Если < 8 — искать ответ в коде/через mcp. Если < 8 и ответ не найден — задавать вопрос. Действовать только при уверенности > 8.
- Если пользователь задаёт вопрос, сначала дать самостоятельный ответ и не изменять файлы автоматически. К изменению кода переходить только после явного согласования или прямой просьбы внести изменение.
- Никогда не использовать expression body (`=`) для функций — всегда явный `return` в теле функции с фигурными скобками `{}`.
- Публичные методы `ViewModel` называть по выполняемой операции предметной области, а не по UI-событию, UI-элементу или методу жизненного цикла `Fragment`: например, `activateUser()`, `deleteUser()` и `finalizeDeletion()` вместо `onUserClicked()`, `onDeleteButtonClicked()` и `onSnackbarDismissed()`.
- В классах сначала располагать все `override`-методы в порядке родительского класса (обычно в алфавитном или жизненном порядке), затем публичные методы по алфавиту, затем приватные методы «водопадом»: метод, вызванный из другого метода, располагать сразу после вызывающего метода; при нескольких вызовах сохранять порядок вызовов.

### Структура замечаний
- Не использовать секцию "История замечаний". Новые замечания добавлять сразу в подходящий подпункт (например, в "Конвенции кода" или "Архитектура"). Если подходящего подпункта нет — создавать новый.

### Сборка
- Для сборки использовать `./gradlew` из папки `Android/`.

### Тесты
- Тесты писать после согласования и реализации файлов. TDD не использовать.
- Для проверок в unit-тестах использовать `org.mockito.kotlin.verify` или `org.hamcrest.MatcherAssert.assertThat`.
- Приватные функции располагать внизу класса с тестами.
- Структура теста: переменные → whenever → вызов методов → проверка результатов.
- Предполагать, что тесты написаны с ошибками; запускать с грепом по ключевым словам ошибок.
- `--tests` не поддерживается с `-p`.
